# ADR-0008 — Mirasim как отдельный backend LLMWorkGUI

- **Статус:** Proposed; реализация и замена существующих маршрутов требуют протокольной приёмки
- **Дата:** 2026-09-24
- **Основание:** запрос владельца проекта добавить поддержку Mirasim и вызов моделей через него
- **Связь:** ADR-0007 остаётся действующим для маршрутов `star-cliproxy`. После приёмки этого ADR он не запрещает параллельный маршрут Mirasim для Codex/AGY. Требования Mirasim внесены в ТЗ 1.4 §6.11b и roadmap 1.3 Phase 7M; прежние Phase 5R evidence и acceptance не переписываются.

## Контекст и наблюдения

Mirasim 0.0.354 установлен на Windows и предоставляет локальный host и `ui-cli`. Проверка 2026-09-24 обнаружила харнесы `codex`, `antigravity`, `grok`; через host успешно завершились ходы Antigravity/Gemini 3.8 Flash Low и Grok/Grok 4.6, а также продолжение той же Antigravity session. Codex/GPT-6 Luna успешно ответил через собственный авторизованный аккаунт при временно отключённом relay; прежняя настройка была восстановлена. Каталог Codex показывает `kimi-k3`, `glm-5.3-flash` и `deepseek-flash`. Владелец подтвердил доступность K3 и GLM в интерфейсе Mirasim. Программный успешный вызов K3 и GLM в этой проверке отсутствует.

При `relay.always=true` запросы Codex к `deepseek-flash` и `gpt-6-luna` завершились соответственно `503 no upstream available` и `422 platform busy`; состояние relay `ok` и наличие модели в каталоге не являются доказательством доступности конкретного route. В `sessions`, `history` и `watch` для успешных ходов были видны модель, session/task ID, terminal outcome и usage, но не полное наблюдаемое соответствие account/route. Команды `ui-cli prompt --text` передают prompt как аргумент процесса. ТЗ §9.3 запрещает секреты в process arguments, поэтому такой канал не может безопасно обслуживать произвольный prompt, который может содержать секреты или restricted данные.

Официальные документы: [CLI и host](https://mirasim.ai/docs/cli), [каталог `ui-cli`](https://mirasim.ai/docs/reference), [модели и аккаунты](https://mirasim.ai/docs/models), [запись и приватность](https://mirasim.ai/docs/privacy). Описание продукта может меняться; контракт определяется runtime capability probe установленной версии.

## Решение

1. Ввести `Mirasim` как **отдельный, явно выбираемый backend**, состоящий из Mirasim host, выбранного харнеса, model ID, режима маршрута и Mirasim session key. Код не объявляет Mirasim синонимом OpenCode, Cursor ACP или star-cliproxy.
2. Существующие backend и их пользовательские сессии сохраняются. Миграция существующего native session ID между backend запрещена. Автоматическая замена `star-cliproxy` или Cursor ACP не выполняется до независимой приёмки нового маршрута.
3. Routing Engine LLMWorkGUI выбирает backend, харнес и модель до отправки. Mirasim host может иметь глобальную политику relay и автоматический fallback; пока нет доказанного per-session pin и observed route, соответствующий маршрут получает `Opaque/ManualOnly` и исключается из автоматического multi-account, retry и silent reroute.
4. Binding сессии фиксирует `mirasimInstance`, `harness`, `model`, `routeMode`, `accountContext` (если доказан), `workspace`, `sessionKey` и версию capability snapshot. Для одной сессии запрещено незаметно менять харнес, аккаунт или маршрут. Изменение модели допускается только в рамках явно подтверждённого продуктового контракта; до его проверки создаётся новая backend session.
5. LLMWorkGUI не переключает глобальные настройки `relay.enabled`/`relay.always` и активный аккаунт Mirasim ради отдельного хода, когда host может обслуживать другие сессии. Не принимает рекламируемый Go plan или `relayStatus=ok` за успешный route probe.
6. Для production prompt необходим документированный или проверенный защищённый канал, передающий содержимое через stdin либо аутентифицированное loopback соединение **без prompt в argv, URI или логах LLMWorkGUI**. `ui-cli --text` допускается только в диагностике на несекретном искусственном prompt. Если безопасный и поддерживаемый канал не найден, product execution остаётся `Unsupported`; реализация не обходит это требование вызовом внутреннего minified `server.cjs` как постоянным контрактом.
7. Mirasim host принадлежит пользователю. Адаптер может подключаться к явно выбранному loopback экземпляру, но не перезапускает, не обновляет и не завершает чужой host или его сессии. При потере соединения применяются существующие `Ambiguous`/reconciliation правила; автоматический повтор prompt запрещён.
8. Terminal success принимается только после проверенного терминального события и сопоставления session/execution ID. CLI exit code 0, `phase=done` при непустом `error`, наличие текста и HTTP-ack не доказывают успех. Если account/route не наблюдаются, UI показывает `Not reported`, а политика ограничивает такой маршрут как opaque. Несовпадение доказанных полей даёт `RouteMismatch`.
9. Запросы разрешений проходят существующую нормализацию. Обнаруженный `bypassPermissions` в настройках некоторых харнесов нельзя считать эквивалентом правил LLMWorkGUI. До проверки `request → user decision → native reply` adapter не объявляет approval capability и не запускает автоматические операции, для которых она обязательна.
10. Mirasim по документации может записывать сырые запросы и ответы по умолчанию. Экран подключения раскрывает этот факт и статус capture/export; LLMWorkGUI не копирует сырые данные в собственные логи и не изменяет пользовательскую настройку записи без отдельного действия пользователя.

## Разрез реализации

Первый срез: read-only discovery, проверка версии/host/capabilities, явный каталог `harness × model`, диагностический тест без пользовательских данных, отображение статуса и ограничений. Второй срез: безопасная передача prompt, create/continue/watch/stop/reconcile, нормализация результатов и UI маршрута. Третий срез: approvals, quota и автоматическое routing только для доказанных capabilities. Каждый срез имеет собственную приёмку; наличие первого не разрешает production prompt.

## Последствия и открытые вопросы

- Mirasim становится потенциально главным backend для Codex, AGY, Grok и моделей Go, но не получает исключений из инвариантов ТЗ о writer lock, route evidence, approvals и терминальном исходе.
- Нужно доказать безопасный payload transport, аутентификацию loopback, поведение `watch` при обрыве, `stop` с terminal confirmation и reattach после рестарта host.
- Нужно выяснить, как Mirasim сообщает фактический account и leg (`Own`/relay) по каждому ходу; отсутствие этого поля ограничивает автоматизацию, а не подменяется значением из каталога или глобальной настройки.
- Поддержка K3/GLM через выбранный харнес принимается только после отдельных реальных, ограниченных вызовов с observed model и terminal outcome. Сообщение владельца о работе в UI фиксируется как полезное наблюдение, а не как программный контракт.
