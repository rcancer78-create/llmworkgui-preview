# ADR-0005: Хранение секретов в Windows

- **Статус:** Accepted
- **Дата:** 2026-09-22
- **Задача:** TASK-005 (Phase 0 — discovery и архитектурные контракты)
- **Связанные документы:** `TECHNICAL_SPECIFICATION.md` §4.1, §6.2, §6.4, §6.16, §8, §9.3, §10; `docs/architecture/THREAT_MODEL.md` §3, §5.1, §5.5; `docs/architecture/DATA_FLOW.md` §4.1
- **Артефакты:** `docs/architecture/THREAT_MODEL.md`, `docs/architecture/DATA_FLOW.md`, `tests/LLMWorkGUI.Backends.ContractTests/SecurityAndStorageContractTests.cs`

## Контекст

ТЗ §4.1 требует: «Секреты — Windows Credential Manager или DPAPI; запрещено хранить API keys в SQLite, JSON, логах или workflow-файлах». §6.2 запрещает передавать secret values в command line и требует redaction до отображения, логирования и записи в audit. §8 разрешает в таблицах только secret reference. §9.3 требует, чтобы credentials не попадали в prompts, logs, crash reports и export, а environment secrets передавались только нужному child process.

Приложению нужны: API keys пользовательских OpenAI-compatible providers, значения headers/query/environment с пометкой `authorization`, `api-key`, `token`, `secret`, `password`, а также ссылки на credentials, которыми владеют OpenCode/plugins. Приложение не должно извлекать или показывать OAuth refresh tokens и не должно читать undocumented credential files (§6.4).

Ограничения окружения: Windows x64, per-user установка без административных прав, единственный пользовательский профиль. Телеметрия продукта по умолчанию выключена, внешний secret store (cloud vault) не предусмотрен и не входит в v1.

## Решение

### 1. Единственный источник значения: Windows secret storage

1. Значения секретов хранятся **только** в Windows Credential Manager (generic credentials текущего пользователя) либо, если Credential Manager доказанно недоступен, в DPAPI-защищённом payload с областью `DataProtectionScope.CurrentUser`.
2. Имя target для Credential Manager детерминированно и не содержит значения секрета: `LLMWorkGUI/secret/<identifier>`, где `<identifier>` — идентификатор URN, то есть часть ссылки вида `urn:llmworkgui:secret:[a-z0-9_-]+` после префикса (`SecretReference.GetIdentifier`). Owner (provider profile/account) и kind остаются reference-only metadata в SQLite и в target не входят, поэтому URN, разделяемый профилем и аккаунтом, и URN без владельца адресуют ровно одну запись Credential Manager. Запись создаётся как `CRED_TYPE_GENERIC` с `CRED_PERSIST_LOCAL_MACHINE`; user name (`LLMWorkGUI`) и comment (`LLMWorkGUI secret payload`) также не содержат значения секрета. Значение в blob — строго UTF-8 без завершающего нуля; пустой, невалидный или терминированный blob считается повреждённой записью.
3. Machine scope, shared scope и любой plaintext-fallback запрещены: при недоступности secret storage соответствующая операция завершается явной ошибкой, а не деградацией к файлу или БД.
4. Значение секрета доступно только процессу, который непосредственно формирует запрос к provider; UI получает только состояние «задан/не задан» и результат проверки соединения без вывода секрета.

### 1.1. Одновременное сосуществование Credential Manager и DPAPI payload

Секрет, записанный до этого решения, лежит в DPAPI-файле `{secrets directory}/{identifier}.secret` (`LLMWGUS1`, entropy `LLMWorkGUI.SecretStore.v1`, `CurrentUser`). Этот формат не меняется и остаётся единственным DPAPI-форматом.

1. Существующая запись Credential Manager авторитетна. DPAPI-файл открывается **только** если `CredRead` вернул `1168` (записи нет) **и** для этого URN нет authority marker.
2. Одна операция записи пишет ровно один backend.
3. Ошибки, не классифицированные как недоступность Credential Manager (`5`, `1312`, `87`, повреждённая запись, нет logon session, не загрузился API), не дают fallback и завершаются типизированной ошибкой без записи и без чтения DPAPI-файла. Fallback применяется только при `50` (not supported) или невозможности загрузить API, и только если authority marker не существовал до вызова: существующий marker означает, что Credential Manager-значение могло существовать ранее, и подмена его старым DPAPI-файлом воскресила бы значение, которого ссылка уже не означает.
4. Authority marker — крошечный reference-only файл `{secrets directory}/{identifier}.cmref`, создаваемый **до** `CredWrite`. Его наличие означает, что DPAPI-файл для этого URN никогда не является fallback, даже если `CredRead` позже вернёт `1168` (например, после удаления записи вне приложения). Ошибка создания marker прерывает операцию до `CredWrite`; если `CredWrite` не удался, а marker был создан этой операцией, marker удаляется обратно, и при невозможности удаления операция завершается без fallback. После успешного `CredWrite` marker сохраняется, а устаревший DPAPI-файл удаляется best-effort и повторяется при следующей ротации или удалении. При явном удалении секрета marker удаляется только после исчезновения обеих репрезентаций. Новый DPAPI-fallback-запись не оставляет marker.
5. **Ограничение окна сбоя.** Падение процесса между созданием marker и `CredWrite` временно делает legacy-секрет нечитаемым: следующий `CredRead` вернёт `1168`, marker есть, поэтому ссылка сообщается как `Missing`, и значение требуется ввести заново. Старое значение при этом **не** воскресает, что и является требуемым свойством. Обратное окно закрыто: credential-first порядок не позволяет новому значению оказаться за старой записью. Authority marker и приоритет чтения — источник истины после сбоя, а не metadata.
6. **Ограничение размера.** Credential Manager ограничивает generic credential 2560 байтами (`CRED_MAX_CREDENTIAL_BLOB_SIZE`) и отвечает `ERROR_INVALID_PARAMETER`. Секрет, который раньше помещался в DPAPI payload, может стать несохраняемым; такое значение отклоняется типизированной ошибкой без записи в DPAPI, а не усекается и не переносится в другое хранилище.
7. `Revoked` в metadata по-прежнему выигрывает у пережившего payload, а `Missing` после восстановления БД из backup остаётся ожидаемым состоянием (§5.3).
8. О выборе backend при необходимости записывается только закрытый код причины и URN, без значения.

### 2. Reference-only URN в SQLite

1. В SQLite `ProviderProfiles` и связанных таблицах хранится только непрозрачная ссылка вида `urn:llmworkgui:secret:openai-api-key` и metadata: kind, владелец (provider profile/account), время создания/последней ротации, состояние.
2. Формат ссылки нормативен: `^urn:llmworkgui:secret:[a-z0-9_-]+$`; uppercase, пробелы, точки, `/`, `..`, дополнительные сегменты и пустой идентификатор запрещены.
3. URN — единственный допустимый способ сослаться на секрет из БД, manifest, конфигурации, экспорта и аудита. Резолвинг URN в значение выполняется только внутри secret service приложения.
4. Дамп БД, backup и диагностический экспорт содержат URN, но не значение; отсутствие записи в Credential Manager даёт явное состояние `Missing`, а не пустой/подставленный секрет.

### 3. Запрет plaintext

Запрещено сохранять или передавать значение секрета:

- в SQLite, JSON, YAML, INI и других файлах конфигурации;
- в `WORKFLOW.ZIP` и любых workflow-файлах;
- в prompts, attachments и сообщениях пользователя;
- в structured logs, crash reports, дампах процесса и diagnostic bundle;
- в process arguments/command line (`argv`) — включая spawn `opencode serve`, `cursor-agent acp` и legacy entrypoint;
- в environment процесса GUI и любого процесса, которому секрет не требуется;
- в телеметрии, audit trail и полнотекстовом индексе.

Допустима передача нужного секрета в заголовке запроса к явно настроенному провайдеру или в scoped environment конкретного child process на время операции. HTTP-проверки не следуют перенаправлениям и не используют общий cookie jar. После завершения процесса переменная не сохраняется приложением.

### 4. Redaction pipeline

1. Все данные, покидающие доверенный контур (логи, audit, search index, preview конфигурации, crash report, diagnostic bundle, UI-отображение), проходят единый redaction pipeline: `identify → classify → replace → verify` (`THREAT_MODEL.md` §5.1).
2. Секреты заменяются типизированным placeholder вида `[REDACTED:<kind>]`; исходное значение не сохраняется даже в зашифрованном виде.
3. Redaction применяется до записи, а не после: config preview/diff, импорт OpenCode configuration и диагностический export показывают уже отредактированные данные и требуют preview.
4. Шифрование at rest рассматривается как дополнительная защита и не заменяет redaction или reference-only хранение.

### 5. Lifecycle и ротация

1. Операции: create, validate (`Test connection` без вывода секрета), rotate, delete. Явный `RotateAsync` перезаписывает значение по тому же target и обновляет `lastRotatedAt`. Сохранение ключа вместе с профилем или аккаунтом использует новую URN: прежний payload остаётся нетронутым до успешной записи владельца. Это позволяет сохранить старый ключ при отказе БД независимо от работоспособности отката хранилища.
2. Удаление секрета удаляет запись в Credential Manager/DPAPI и переводит URN в состояние `Revoked`; зависимые routes становятся неeligible до повторного ввода.
3. Восстановление БД из backup не восстанавливает секреты; отсутствующие URN отображаются как `Missing` и требуют повторного ввода — это ожидаемое поведение, а не ошибка миграции.
4. Credentials, которыми владеют OpenCode/plugins, не копируются приложением; bridge получает только те ссылки/состояния, которые разрешены контрактом §6.4.

## Последствия

- SQLite backup, diff БД и диагностический экспорт безопасны по определению: в них нет значений секретов.
- UI обязан иметь write-only поле для API key и никогда не показывать сохранённое значение; тест соединения возвращает только статус.
- Adapter'ы обязаны формировать child process environment явно и точечно; любая передача секрета через argv считается дефектом.
- Redaction pipeline становится обязательной зависимостью логирования, аудита, поиска и экспорта с Phase 1.
- Contract tests фиксируют URN-контракт и отсутствие секретов/приватных путей в артефактах.

## Риски и ограничения

- **Credential Manager quota/поведение.** Windows ограничивает generic credential 2560 байтами и может отказать в записи с `ERROR_INVALID_PARAMETER`; лимит проверяется до создания authority marker, и превышение возвращается типизированной ошибкой, а не усечением значения и не откатом к DPAPI (§1.1.6).
- **Окно сбоя между marker и CredWrite.** Падение в этом окне делает legacy-секрет временно нечитаемым и переводит ссылку в `Missing`; значение вводится заново. Старое значение не воскресает, поэтому цена ограничена повторным вводом (§1.1.5).
- **DPAPI привязан к профилю Windows.** Смена пользовательского профиля делает DPAPI payload недоступным — это принимается как защита, а не баг.
- **Secrets вне приложения.** Приложение не контролирует файлы и historical logs сторонних CLI; они не копируются без sanitized preview, но их очистка не обещается.
- **Redaction не абсолютна.** Новые форматы секретов требуют обновления паттернов; reference-only хранение снижает последствия пропущенного паттерна.
- **DPAPI fallback.** Используется только при доказанной недоступности Credential Manager (`50` или незагружаемый API) и только для ссылки, у которой не было authority marker; выбор фиксируется в audit закрытым кодом причины и URN, без значения секрета.

## Альтернативы

- **Plaintext API key в SQLite (даже зашифрованный ключом приложения)** — отклонено: нарушает §4.1/§8 и создаёт единую точку утечки через backup/дамп.
- **Секреты в файле конфигурации с ACL** — отклонено: файл попадает в диагностический экспорт, diff и backup; ACL не защищает от чтения тем же пользователем.
- **Секреты в command line/manifest** — прямо запрещено §6.2: argv виден другим процессам и попадает в логи процессов.
- **Machine-scope DPAPI/Credential Manager** — отклонено: per-user модель приложения и отсутствие admin-прав; machine scope расширяет доступ.
- **Внешний cloud vault** — вне области v1 (§14), добавляет сетевую зависимость и новый secret flow без требования ТЗ.
- **Подстановка пустого секрета при отсутствии записи** — отклонено: маскирует ошибку и может привести к отправке запроса с неверными credentials.


### Уточнение 4 октября 2026: пользовательские HTTP-заголовки

Миграция 016 добавляет `ProviderProfiles.CustomHeadersJson` и ревизию профиля. Обычные значения хранятся в metadata; отмеченные секретом значения и имена авторизации, token, cookie и API-key сохраняются только как URN с назначением `ProviderHeader`. Сохранённый секрет не возвращается в форму: пустое поле оставляет прежнюю ссылку, новое значение заменяет её, удаление строки удаляет заголовок. Имя должно быть уникальным без учёта регистра; не более 64 заголовков, 256 символов имени и 32768 символов значения; управляющие символы, кроме TAB, запрещены.

Замена заголовка использует новую ссылку и общий commit профиля. При отказе commit новые секреты компенсируются, прежние остаются доступны. Ревизия предотвращает перезапись конкурентного изменения профиля, включая прямой repository writer. После commit устаревшая ссылка отзывается с проверкой других владельцев. Обновление списка моделей/формы является отдельной операцией: его сбой не отменяет и не скрывает уже сохранённый профиль.

Перед GET `/models` и POST `/chat/completions` проверяются актуальная привязка к профилю/аккаунту, зарегистрированное назначение и состояние. Для bearer-ключа требуется `ProviderApiKey`, для секретного заголовка — `ProviderHeader`. `Missing` остаётся отказом даже при наличии файла, пока пользователь явно не заменит значение; `Revoked` также не разрешает отправку. Локальный отказ секрета не является наблюдаемым HTTP 401/403 и не блокирует соседние маршруты как ошибка авторизации провайдера.

Старые ссылки с назначением `Unspecified` автоматически не получают новое назначение. Для их использования в HTTP-провайдере требуется заново сохранить API-ключ; создаётся новая типизированная ссылка, прежнее значение другого назначения не перезаписывается. Новые проверки не выполняют вход, ротацию или миграцию личных аккаунтов без действия пользователя.

Этот путь сохраняет профиль приложения, показывает скрывающий секреты preview и выполняет локальные проверки подключения/моделей/здоровья. Подтверждение preview не устанавливает конфигурацию во внешний сервер OpenCode. Отказ очистки после commit регистрируется; принудительное завершение процесса и недоступность одновременно metadata/payload storage не дают гарантии завершённой очистки и требуют отдельной recovery-проверки.


### Удаление профиля и восстановление очистки (4 октября 2026)

Удаление выбранной версии профиля, отзыв его неразделяемых зарегистрированных ключей/заголовков и постановка ссылок в `PendingSecretDeletions` фиксируются одной транзакцией SQLite. Ошибка этой транзакции оставляет профиль и payload без изменений. Учитываются действующие ссылки других профилей и аккаунтов независимо от полноты `SecretReferenceOwners`; неизвестный владелец препятствует автоматическому отзыву. `RevokeProviderApiKeyAsync` снова имеет узкий контракт: он не отзывает заголовки.

Значения удаляются из хранилища после commit. Отказ удаления не возвращает уже отозванному ключу доступность: очередь сохраняется, UI сообщает об ожидающей очистке, primary instance повторяет её при запуске. Вторичный экземпляр не выполняет очистку. Startup recovery проверен на synthetic SQLite/DPAPI; принудительное завершение настоящего процесса в каждой точке ещё не является проверенной гарантией. Ссылки несовпадающего назначения автоматически не удаляются.

История `ProviderProfileRevisions` переживает удаление: явное создание того же ID получает более новую версию, поэтому старое сохранение/удаление существовавшего профиля не применяется к новой записи. `Revision=-1` означает явную попытку создания новой записи; это не токен прежней инкарнации. Условное сохранение возвращает фактически записанную версию в той же транзакции.

Сохранение API-ключа профиля или учётных данных аккаунта создаёт отдельный payload и регистрирует новую URN до записи владельца. При отказе записи компенсируется только новая ссылка; прежний ключ и binding сохраняются даже при отказе очистки новой ссылки. Это отличается от отдельной операции `RotateAsync`, которая по-прежнему вращает явно указанную URN на месте.

Триггеры migration018 при замене API-key/header/account binding проверяют фактические ссылки всех профилей и аккаунтов, независимо от полноты owner metadata. Только прежние ссылки ожидаемого назначения без оставшихся потребителей переводятся в `Revoked` и попадают в `PendingSecretDeletions` в той же транзакции. Очистка payload выполняется после commit, а при её отказе или прерывании — primary supervisor при следующем запуске. Смена одного владельца общего ключа не меняет значение для остальных. Ссылки другого назначения и `Unknown` owners не отзываются автоматически.

Секретность HTTP-заголовков определяется общим `IsSensitiveHeaderName` для формы, persistence, preview и diagnostic export, включая signature/cert/pass. Это более консервативная политика, чем распознавание обычных JSON-полей с метриками токенов. UI не привязывает сообщение об успешном сохранении к конкретному механизму Credential Manager/DPAPI.

Явный отзыв аккаунтного ключа отказывает, если та же URN используется другим аккаунтом, API-ключом/заголовком профиля или имеет Unknown owner. Своя binding не препятствует отзыву отдельного ключа. Отказ не меняет metadata, payload и очередь. Репозиторий аккаунтов проверяет supervisor перед записью и после открытия соединения; форма вторичного экземпляра разрешает чтение, но отключает изменения.
